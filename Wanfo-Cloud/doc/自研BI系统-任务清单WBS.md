### S0-T04 选型决策说明（务必重视）

这是整个项目**唯一不可逆的技术决策**，三个选项：

| 选项 | 优势 | 代价 | 适配场景 |
|---|---|---|---|
| **Apache Calcite** | 成熟的 SQL 解析/校验/下推；跨源联邦查询开箱即用；方言生态丰富（含 Doris） | 2,104 行才能吃透（DataEase 的 CalciteProvider）；学习曲线陡；AST 与业务模型有一层阻抗 | 数据源多、需跨源 JOIN |
| **自研 SQL 层** | 完全可控，无学习成本 | 解析器 + 优化器 + 方言适配全是深坑；跨源 JOIN 几乎从零 | 只支持 1~2 种数据库 |
| **DuckDB 嵌入式** | 性能极强，纯 SQL 即可实现跨源；部署轻 | Java 侧绑定较新；需处理各数据库的 SQL 方言差异 | 数据量大、内存内分析 |

**建议**：首批只支持 2~3 种数据库且**不需要跨源 JOIN** → 自研 SQL 层最划算；一旦需要跨源，直接上 Calcite，别自研。

### S2-T04 图表定义建模要点

图表定义是整套系统最复杂的元数据。建议用 **JSON 字段 + 少量结构化列** 的混合模式：

~~~text
core_chart_view
├── id / name / chart_type / dataset_id      (结构化，可索引)
├── x_axis          JSON   维度轴配置数组
├── y_axis          JSON   度量轴配置数组
├── x_axis_ext      JSON   次要维度（堆叠、拆线）
├── y_axis_ext      JSON   次要度量（双轴）
├── drill_fields    JSON   下钻路径
├── ext_stack       JSON   堆叠扩展
├── ext_bubble      JSON   气泡大小/颜色映射
├── custom_filter   JSON   过滤器树
├── style           JSON   样式
└── ui_config       JSON   交互配置
~~~

**经验**：纯结构化建模会导致几十张关联表，查询时 N+1 严重；纯 JSON 会失去索引能力。混合模式是 DataEase 的做法，可直接借鉴。

### S4-T08 必须处理的类型坑（血泪清单）

| 坑 | 现象 | 处理 |
|---|---|---|
| BIGINT 精度丢失 | Java Long → JSON → JS Number，超过 2^53 精度丢失 | 后端统一序列化为字符串，前端按需解析 |
| DECIMAL 精度 | Doris/MySQL 的 DECIMAL 在 JDBC 返回 BigDecimal | 保持 BigDecimal，序列化时按精度转字符串 |
| 时间时区 | 各库时区语义不同（JVM/库/连接三层） | 统一 UTC 存储，展示层转换 |
| 空值语义 | NULL 与空字符串、0 在不同库处理不同 | 查询层统一 |
| 字符集 | MySQL utf8mb4 vs PostgreSQL UTF8 | 建库即统一 |
| 排序稳定性 | 同值排序导致分页错乱 | 强制追加唯一列做 tiebreaker |

### S5-T06 变量机制设计（嵌入式集成的关键）

~~~text
用户 SQL:  SELECT dept, SUM(amount) FROM sales
            WHERE dept = [参数变量] AND dt >= [起始日期]
                              ↓
运行时取值来源（优先级）：
  1. 大屏外部参数（URL 传参）
  2. 登录用户属性（如用户所属组织）
  3. 数据集默认值
  4. 兜底常量
~~~

**这个机制是「把 BI 嵌入主系统」的基础**——主系统跳转到 BI 页面时携带参数，BI 自动按参数过滤数据。

### S8-T13 属性映射行权限设计（最容易做错的部分）

这是「数据权限隔离」真正落地的机制。三种实现路径：

| 路径 | 规则来源 | 灵活性 | 实现难度 | 适用 |
|---|---|---|---|---|
| 固定规则 | 管理员写死 WHERE 条件 | 低 | 低 | 固定报表 |
| **属性映射** | 字段值 = 用户属性值 | **高** | 中 | **主流方案** |
| 自定义 SQL | 管理员写一段 SQL 返回可见范围 | 最高 | 高（安全风险） | 复杂场景 |

属性映射的标准做法：

~~~text
用户表关联：用户 zhangsan → dept = "华东区"
数据集字段：orders.region
映射配置：   orders.region ← user.dept
生成 SQL：   WHERE orders.region = '华东区'
~~~

**注意安全风险**：自定义 SQL 方式必须做权限校验，否则用户可借此越权查询任意数据。

### 权限体系验收标准

- [ ] 用户 A 只能看到本部门数据，用户 B 能看到全公司数据，配置在后台完成无需改代码
- [ ] 无权限的敏感字段（如手机号）在 API 响应中**不存在**（用抓包验证，不是看前端）
- [ ] 脱敏在服务端完成，抓包可见脱敏后的值
- [ ] 权限变更 10 秒内生效
- [ ] 权限测试工具能准确预览任意用户的实际数据范围

**这个版本的能力**：接 Doris 和 MySQL → 建数据集 → 拖拽搭看板 → 按组织隔离数据 → 导出 Excel。足以替代公司内部 80% 的报表需求。

## 附录 C：三条铁律

**第一，权限必须在取数链路里做，不能靠前端隐藏。**
列级权限要求「无权限字段不出现在响应中」，行级权限要求「WHERE 条件注入 SQL」。这两个动作都必须在 S6-T02 取数链路中完成，且在 S6 之前就完成 S8 的核心部分。

**第二，类型问题必须用真实脏数据测。**
建一个「特殊数据样本库」，里面放：BIGINT 超过 2^53 的 ID、超长中文与 emoji、emoji 与特殊符号、空字符串与 NULL 的区别、负数与零、极值日期。这些坑不主动测，上线后一定爆。

**第三，数据同步不是 BI 的活。**
MySQL → Doris 由 Flink 承担。BI 只做「查」和「展示」。把同步塞进 BI 项目，等于凭空多出 3~4 人年，而且做出来也不如现有的 Flink CDC。
