## 连接排查与限制

Docker 中 dataease、de-mysql 均为运行且健康。进一步读取健康检查发现，其成功条件只是容器内 8100 TCP 端口可打开，不能证明浏览器页面、查询 API 或 WebSocket 正常。

主机 8100 存在 Docker backend 与 WSL relay 监听，尚不能据此确定连接重置的根因。DataEase 日志另有连接 `example.internal:9030` 时 EOF 的警告；该问题属于 Doris 连接，未证明它导致本次官方示例预览失败，不能混为一个根因。

浏览器进入连接错误页后，后续操作也受到浏览器 URL 策略限制。未绕过策略，未重启服务、修改网络设置或数据源，未修改官方资源。

## 恢复后的执行顺序

1. 确认浏览器能够新开并正常加载参考系统，重新打开现有副本，核实配置持久化。
2. 确认绑定的具体指标，取得“全量/冷/热”的可比较结果；验证默认值、应用、清空、重置和未绑定组件。
3. 在副本中完成一次发布，改变草稿并对照消费页，验证重新发布及恢复发布稿。
4. 验证联动/钻取及条件组合，再验证模板有效字段映射与安全的刷新/错误恢复。
5. 将实际行为转化为自研平台验收条件；参考实测不能替代自研测试。

企业功能仍受限于缺少授权企业环境或对应源码，不纳入本次通过项。

## 后续连接定位（2026-10-16）

针对用户要求排查无法打开，进行了 HTTP 分层诊断：容器内 `127.0.0.1:8100/` 返回 200；Windows 主机通过 IPv4 `127.0.0.1:8100/` 返回 200，约 0.20 秒；强制 IPv6 访问 `localhost:8100/` 建立连接后 8 秒没有响应。主机 `::1:8100` 的具体监听属于 wslrelay，Docker backend 另有通配监听。故当前故障定位在本机 IPv6/WSL 转发路径，尚未确定 relay 内部异常原因；不是 DataEase 整体停机。

浏览器新开 `http://127.0.0.1:8100/` 已正常渲染登录表单，证据为 `02-ipv4-login-recovered.png`。IPv4 地址可作为当前访问入口。域名变化后需要重新登录；未修改防火墙、hosts、系统 IPv6，也未重启 WSL 或 Docker。此结果仅恢复页面可达性，尚不代表前述业务验证通过。
