# ADR-DP-035：数仓 MVP 的分析目标选型

- 状态：MVP 试点决策；生产定型待容量与恢复验收
- 日期：2026-10-28
- 关联：DP-035、DP-036～DP-041

## 决策摘要

数仓 MVP 以 **ClickHouse 作为独立分析目标试点**，先在本地开发/验收环境使用单节点实例验证批量入仓、聚合查询、分层模型与 BI 消费。该决定不授权把 ClickHouse 当作平台元数据库或业务事务库，也不构成生产容量、HA 或 SLA 承诺。

当前本机 Docker 有独立 MySQL 平台元数据库、PostgreSQL 17 测试容器和运行中的 ClickHouse 25.8.33.6 容器；五个 `wanfo_wh_*` 空逻辑库已初始化并查询确认，HTTP 接口要求认证。最小权限分析账号、BI 应用连接、数据备份尚未完成验收。该实例存在不代表目标权限、数据备份或生产可用性已完成。PostgreSQL 继续作为合成业务源/连接器验收库；真实业务数据不进入本次试点。

## 背景与边界

数据平台需要将业务数据批量写入独立分析目标，并承载列裁剪、扫描聚合、主题汇总和 BI 查询。三个存储职责保持分离：

| 存储 | 负责内容 | 不负责内容 |
|---|---|---|
| 平台元数据库（当前 MySQL） | 账号/权限引用、数据源引用、资产、任务定义与运行、审计、版本和水位元数据 | 业务明细、数仓主题宽表、图表结果快照 |
| 业务数据源（本地 PostgreSQL 17 作为验收源） | 业务交易和事务写入，是本次抽取的只读来源 | 平台治理元数据、分析加工结果 |
| ClickHouse 分析目标（本地实例运行；逻辑库/账号待验收） | ODS/DWD/DWS/ADS 逻辑层、批量入仓、聚合及受控 BI 试点 | 登录/权限事实、数据源凭据、扫描配置、业务事务主库 |

平台只持有目标连接的加密凭据和目标标识；运行任务使用单独的写入身份。源身份只读，平台管理账号与目标写账号分离。任何数据写入必须由已发布作业显式指定目标库、表和分区。

## 候选方案

| 方案 | 优点 | 主要代价/风险 | 本轮判断 |
|---|---|---|---|
| PostgreSQL 作为平台元数据与数仓共用库 | 开发运维简单；事务和更新删除语义直观 | OLTP/治理事务和宽表扫描争用资源；难以维持存储职责分离；后续需要迁出 | 不选作本期目标。保留为源和小规模外部目标备选 |
| ClickHouse 独立目标 | 面向分析扫描和聚合；现有连接器目录已登记；可与 MySQL/业务库隔离 | 需要批量写入、排序键和分区设计；频繁小写入、更新删除、逐行事务不是合适的默认路径；必须验证恢复和权限隔离 | **选作 MVP 试点** |
| 外部托管数仓/湖仓 | 运维托管和弹性扩展可能更好 | 供应商、成本、网络、数据驻留和账号体系未确认；目前没有可复用的目标实例 | 本期暂不引入，触发条件见下文 |

选择依据是项目的分析型、批处理目标和用户此前提出的 ClickHouse 本地验证方向。ClickHouse 的 MergeTree 家族面向高数据写入率和大数据量，并依赖排序键、分区裁剪和后台合并；单次插入过小会增加写入与合并开销。因此 DP-037 必须采用批量写入并基于真实验收数据选择排序/分区设计。[ClickHouse MergeTree 文档](https://clickhouse.com/docs/engines/table-engines/mergetree-family/mergetree)、[ClickHouse 批量插入文档](https://clickhouse.com/docs/optimize/bulk-inserts)。PostgreSQL 继续适合承担本地源与事务型场景，其 MVCC 保证读写并发的一致快照；这并不表示应把 OLTP 源库改作本项目的唯一分析目标。[PostgreSQL MVCC 文档](https://www.postgresql.org/docs/current/mvcc-intro.html)

## 目前可确认的需求与待采集数据

现有文档确定了最小批处理数仓、业务源/平台元数据库/目标隔离、源到目标对账、组织/租户过滤及一张 BI 试点看板。以下容量参数没有真实依据，不在本 ADR 中伪造数值：

| 参数 | 当前值 | 采集方式/决策影响 |
|---|---|---|
| 首个主题源表行数和磁盘大小 | 待选主题后统计 | 从测试源统计；决定全量窗口、抽取分页和验收样本 |
| 每日新增量及增长率 | 未知 | 业务负责人提供或观察一段周期；决定分区与保留策略 |
| 首次全量完成时限 | 未定义 | 与业务确认；用目标资源基准测试 |
| 增量新鲜度目标 | 未定义 | 先按计划批处理能力验收，不承诺实时；与报表使用人确认 |
| BI 并发、查询响应目标 | 未知 | 用代表性看板压测；确定查询并发、内存和隔离限额 |
| 在线保留/历史保留 | 未定义 | 按业务与合规要求确认；物理 TTL 不能早于授权保留期 |
| 租户/组织模型 | 需逐业务确认 | 入仓保留租户/组织键；服务端行权限在写入和消费两端一致 |
| 备份、RPO/RTO、HA | 未定 | 生产环境级别不可由单节点容器推断；需运维负责人确认并演练 |
| 资源/成本预算 | 未知 | 本地试点只验证行为；生产资源与托管费用需容量测试后估算 |

## MVP 工作负载约束

1. 仅批处理全量和可恢复的批量增量；初版不引入 Kafka、CDC 实时流或跨区域复制。
2. 先做一个合成零售主题：订单头、订单明细、商品、组织/区域维度；数据使用合成数据，包含更新、迟到、重复和删除标记样例。每行应带源标识、抽取批次、水位/更新时间和租户/组织键。
3. 以 10k 行量级作为合成基线，另提供可配置的 100k/1M 行压测档位；这些是测试档，不是生产容量承诺。每档记录数据生成参数、压缩后磁盘占用、写入时长、资源峰值、代表性聚合查询 P50/P95。
4. ClickHouse 写入使用缓冲批次；默认目标先按 10k 行左右一批压测，再比较更小/更大批次，生产参数由压测定。官方文档推荐更大批次并减少 insert 次数，但具体阈值以本平台的数据形状和资源为准。
5. 用 staging/批次标识验证、对账后才发布；重复批次重试必须幂等。任何依赖后台合并才能最终去重的行为，都不能作为查询正确性保证。
6. 目标上的数据集和图表查询都必须保留服务端租户/组织权限；客户端过滤不能作为隔离边界。

## 重新评估/切换触发条件

满足任一条件时暂停扩容，补做目标引擎评审：

- ClickHouse 批处理窗口、并发或资源预算无法通过代表性压测；
- 项目主要需求转成高频单行更新/强事务写入；
- 出现多租户隔离、数据驻留、HA/RPO/RTO 要求而单实例部署无法满足；
- 生产团队无法承担 ClickHouse 备份、监控、升级和故障演练；
- 外部数仓已有采购、网络和数据治理条件，且全生命周期成本更低。

## DP-035 验收门

在宣称 DP-035 完成前，需补齐并评审：

- 一个真实业务方确认的首期主题、关键指标和权限样例；
- 每张源表的行数、大小、增量/更新/删除语义；
- 刷新时效、并发、在线与历史保留要求；
- 基线压力测试及单机资源/磁盘/成本估算；
- 租户/组织过滤责任人、备份恢复责任人、RPO/RTO；
- ClickHouse 开发/验收目标库和账号隔离配置。

因此，本记录给出了可推进 MVP 的**试点引擎建议**，但由于上述容量和业务参数缺失，DP-035 仍标为“有条件待验收”，不作为生产架构最终批准。
