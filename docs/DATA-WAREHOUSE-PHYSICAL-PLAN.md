# ClickHouse 数仓物理规划（MVP）

> 状态：开发/验收基线；生产容量、保留期、备份恢复与账号授权待评审。  
> 关联：DP-035～DP-041、[引擎 ADR](DATA-WAREHOUSE-ENGINE-ADR.md)

## 1. 存储边界

- 平台元数据库继续使用 MySQL，只保存数据源引用、任务定义/运行、资产、审计和水位等控制面信息。
- PostgreSQL 等业务库作为只读抽取源；抽取过程不向源库建表或写入。
- ClickHouse 是独立分析目标，只存经过批准的分析数据。BI 只有在模型发布后才读取目标层。
- 开发、验收、生产必须使用独立实例或至少独立凭据和数据库；禁止把本地开发凭据复制到部署配置。

## 2. 逻辑层和命名

`deploy/clickhouse/bootstrap-layers.sql` 可幂等创建空的 MVP 数据库。每个数据库代表一个逻辑层，避免将其误认为独立集群：

| 数据库 | 用途 | 写入者 | 下游可见性 |
|---|---|---|---|
| `wanfo_wh_staging` | 单次作业暂存、完整性校验与发布前检查 | 入仓执行身份 | BI 不直接读取 |
| `wanfo_wh_ods` | 来源结构映射后的原始明细，保留源键和抽取批次 | 入仓执行身份 | 仅治理/加工角色 |
| `wanfo_wh_dwd` | 清洗、统一类型和业务粒度后的明细事实/维度 | 已发布加工作业 | 受控模型使用 |
| `wanfo_wh_dws` | 面向主题的汇总和公共指标中间层 | 已发布加工作业 | 受控模型使用 |
| `wanfo_wh_ads` | 已发布的应用/报表消费模型 | 发布流程 | BI 服务只读 |

建议表名使用小写 `主题_实体`，例如 `retail_order_header`。表级定义必须记录源系统标识、源主键、批次 ID、抽取时间/水位和租户/组织键（适用时）。列名、类型和业务口径由版本化模型定义维护。

## 3. 物理设计门禁

- 引擎优先采用 MergeTree 家族，但每张表需先确认数据粒度、排序访问路径、更新/删除语义和批量写入方式。
- 分区字段应按典型查询和生命周期确定；禁止仅因“按月”方便就对小表过度分区。TTL 必须晚于已批准的在线保留期限。
- 不把后台 merge 后的去重当作查询正确性保证。作业须用批次/版本校验和原子发布策略保证重跑幂等；物化发布方案留给 DP-039 定义。
- 先限制单节点资源和并发，记录数据集大小、写入批量、耗时、磁盘增量、资源峰值及代表性查询 P50/P95；没有容量数据时不宣称生产容量。
- 本地容器只用于合成数据。目标实例需使用独立写入身份、只读 BI 身份和单独的运维身份；凭据通过部署密钥注入，不能提交到仓库。

## 4. 备份、恢复与账号

- MySQL 元数据库与 ClickHouse 分别制定备份和恢复流程；恢复点与保留周期由业务方/运维确认，不从开发容器推断 RPO/RTO。
- ClickHouse 账号按职责拆分：入仓身份仅能写目标范围；BI 身份对已发布 ADS 模型只读；运维身份不得供应用运行时使用。
- 在目标 ClickHouse 版本确认、账号可见性/授权评审通过之前，仓库只提供空数据库初始化 SQL，不预置用户或宽泛授权。
- 本地 DP 验收另提供 `deploy/clickhouse/warehouse-runner-role.sql`：元数据发现 + ODS 入仓，以及管道 `pipe_*` 发布所需的 DWD/DWS/ADS 建表/写入（不含全局 ALL）；该脚本不创建用户、不设置口令。创建独立用户后，才将 `dp_warehouse_runner` 角色赋给该用户并在 BI 注册 ODS 目标。
- 每次恢复演练记录版本、备份范围、恢复耗时、校验结果和差异；生产启用 TLS，并验证服务端证书校验。
