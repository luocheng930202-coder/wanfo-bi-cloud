## 1. 计划目标

按依赖逐步把现有 BI 平台扩展为可运营的数据平台。先交付资产目录与元数据采集，再补齐最小批处理数仓主线（独立分析目标、全量/增量入仓、分层建模、物化、源目标核对和 BI 试点），随后交付质量、流程、血缘/变更安全，最后完善数据服务和生产运营。每阶段设验收门，权限、状态机和资产身份未稳定前不扩展到下一层。

本计划不重写已有 BI，不预先拆微服务，也不承诺通用湖仓产品、对象存储湖仓或复杂实时 CDC。最小分析型数仓和批量入仓属于本期核心范围。

## 2. 排期假设

- 以两周迭代为一个 Sprint；计划按一个小型跨职能团队并行推进：后端 2 人、前端 1 人、测试/数据环境 1 人部分投入，架构/安全按需评审。
- 这是工程量级和依赖计划，不是对具体日期的承诺。若主要由 1 名全栈开发完成，预计日历周期将显著拉长。
- 每个 Sprint 预留约 20% 容量处理缺陷、CI 修复、数据库差异和既有 BI 回归；阶段末另设验收窗口。
- PostgreSQL、ClickHouse、MySQL 等真实实例应由开发环境提供；生产结构只做授权的只读核验，真实业务数据不用于开发验收。
- 当前已有代码或 SQL 草案必须先构建/迁移/授权核对，未验证的实现不计入已完成进度。

**初步估算：**资产目录与元数据采集 MVP 约 8 周；数仓 MVP 再增加约 6 周；P0 治理闭环基准约 26 周；数据服务与生产运营再需约 6 周。当前建议基准排期 **32 周**，预留风险缓冲后按 **28–36 周** 管理，并在 Sprint 0 结束后按实际吞吐重新估算。通用湖仓与实时 CDC 等 P2 不纳入本期。

## 4. Sprint 计划

### Sprint 0（第 1–2 周）：环境、权限和数仓需求基线

**目标**：消除迁移、权限、存储目标和首期业务用例的不确定性。

- 完成 DP-001～DP-003：核实目标环境迁移/生产 DDL 差异、备份恢复、URN/权限规则及连接器矩阵。
- 推进 DP-035：已有 [分析目标选型 ADR](DATA-WAREHOUSE-ENGINE-ADR.md)，将 ClickHouse 定为 MVP 试点候选；需业务方提供容量/SLA/保留与组织隔离样例，并以合成数据压测后完成生产定型。
- 复核未验证的 Connector Registry 与 V27 草案；明确首个业务主题和验收数据集。

**退出条件**：迁移路径及试点引擎 ADR 有记录；生产目标定型有业务容量数据、压测和运维评审支撑；不将开发库状态当作生产结论。

### Sprint 1（第 3–4 周）：连接器目录与治理模型

- 完成 DP-004、DP-005：服务端连接器能力目录、V27 migration、空库安装和 V26 升级验证。
- 建立目录/扫描 Mapper、DO、索引规范；评审扫描状态机、并发和错误脱敏。
- 设计分析目标的凭据、访问控制和配置生命周期，不在平台元数据库保存业务明细。

**退出条件**：CI 构建通过；两种 schema 路径成功；既有 BI 数据不变。

### Sprint 2（第 5–6 周）：扫描服务和连接器

- 完成 DP-006、DP-007：扫描配置/运行状态及至少两类数据库元数据 adapter。
- 完成 DP-012 首批：审计、Trace/request ID、超时、对象上限和异常脱敏。
- 明确源端只读账号、连接池和扫描负载限制。

**退出条件**：真实测试实例采集成功；不读取业务行；失败保留旧快照。

### Sprint 3（第 7–8 周）：资产目录 MVP 与 BI 回填

- 完成 DP-008～DP-011：资产快照/diff、目录搜索详情、权限过滤和 BI 资源回填。
- 验证大 schema 分页、撤权和敏感字段边界。

**退出条件**：URN、数量、owner/权限对账；字段变化可解释；越权结果不可枚举。

### Sprint 4（第 9–10 周）：分析目标与物理分层

- 完成 DP-036：建立独立分析型目标、最小权限账号、ODS/DWD/DWS/ADS 逻辑分层和物理命名约定。
- 定义分区、生命周期、备份恢复和环境配置；保持平台元数据与业务明细分离。

**退出条件**：目标库连通、权限最小化；部署/恢复说明和目标资源预算通过评审。

### Sprint 5（第 11–12 周）：全量与批量增量入仓

- 完成 DP-037：一个真实源的全量初始化、增量水位、更新/删除语义、检查点、失败恢复和回补。
- 为批次/run/分区记录源范围、目标位置、水位、计数和执行状态。

**退出条件**：中断续传、重复执行幂等；schema 变化不会静默丢列；源库负载在预算内。

### Sprint 6（第 13–14 周）：主题建模、发布核对和 BI 试点

- 完成 DP-038～DP-041：首个事实/维度主题模型、staging 物化发布、源目标对账/新鲜度门禁、BI 切换和回退。
- 将至少一个数据集及关联图表/看板接入数仓模型，核对业务指标和组织/租户权限。

**退出条件**：M4 数仓 MVP 通过；关键指标一致；差异可定位；失败可回退；分析目标恢复路径演练完成。

### Sprint 7（第 15–16 周）：质量模型与规则迁移

- 完成 DP-013、DP-014：规则版本、质量任务/结果模型与现有 JSON 规则迁移。
- 质量规则支持源表及数仓模型，明确全量/抽样口径。

**退出条件**：回填可重跑、规则语义等价；数据源范围和权限过滤正确。

### Sprint 8（第 17–18 周）：质量运营闭环

- 完成 DP-015～DP-017：调度、运行结果、趋势、问题闭环和轻量画像。
- 将 WH-006 的核对差异/新鲜度作为质量可见项，保留源与目标的口径区别。

**退出条件**：暂停/重试/失败状态正确；结果脱敏；全量和抽样不混淆。

### Sprint 9–10（第 19–22 周）：加工 DAG 与数仓物化

- Sprint 9：完成 DP-018、DP-019，建设带 schema 校验的 DAG 模型及编辑器。
- Sprint 10：完成 DP-020、DP-021，执行器、节点状态、取消/重试、只读回放、发布及回滚；将受控目标物化纳入执行器。
- 同步完成 DP-022 的统一任务中心适配设计。

**退出条件**：无任意脚本执行；失败发布保留旧版本；回放不写业务源；物化和分区回补幂等。

### Sprint 11–12（第 23–26 周）：血缘、结构变化与指标治理

- Sprint 11：完成 DP-023、DP-024，先表级血缘，再按能力支持字段级，覆盖数仓模型来源。
- Sprint 12：完成 DP-025～DP-027，变更预览/批准/迁移回滚及指标口径治理。

**退出条件**：核心 BI 消费链路可追溯；破坏性变更阻断；指标跨图表/API 口径一致。

### Sprint 13–14（第 27–30 周）：数据服务和运营整合

- 完成 DP-028～DP-030：统一服务目录、受控 API、Key 轮换、权限/配额、审计、告警和保留策略。
- 复用现有 BI 导出/订阅事实；通过策略选择受控源或已发布数仓模型。

**退出条件**：撤权立即生效；日志无密钥/响应正文；真实通知和失败重试通过环境验收。

### Sprint 15（第 31–32 周）：生产候选与恢复验收

- 完成 DP-031：在接近生产版本的备份恢复副本执行升级/恢复演练。
- 验证元数据库和分析目标的 TLS、容量、连接池、任务资源隔离、审计保留、追踪关联及告警。
- 冻结范围，仅修复缺陷并完成发布/回滚手册。

**退出条件**：M8 通过；生产负责人签核；遗留事项有负责人和目标版本。
## 5. 并行安排和关键路径

```mermaid
flowchart LR
  A[环境/权限/URN 基线] --> B[Registry 与 V27]
  B --> C[扫描器与数据库连接器]
  C --> D[资产版本/diff]
  D --> E[目录 API/UI/BI 回填]
  E --> W[独立数仓/批量入仓/分层模型]
  W --> F[质量任务闭环]
  W --> G[流程 DAG 与物化]
  F --> H[血缘与影响分析]
  G --> H
  H --> I[结构变更安全与指标治理]
  I --> J[数据服务与生产运营]
```

可并行工作：

- Sprint 1 中，后端模型和前端目录交互原型可并行，但真实 API 对接以权限/URN 定稿为前提。
- 扫描器开发期间，安全/QA 可编写驱动矩阵、越权和脱敏验收用例。
- 质量模型与目录 UI 的非依赖原型可并行；流程 DAG 数据模型需等待资产 URN 和任务运行契约稳定。
- 产品/业务方应在 Sprint 0 提供指标口径样例、结构变更场景、通知渠道和保留要求；缺少这些输入时相关功能不能宣称业务验收完成。

## 6. 发布节奏与分支策略

- 每个任务通过独立 PR/代码评审进入开发分支；PR 标题和说明写清功能点、迁移版本、兼容影响及验证结果。
- `main` 保持可构建、可发布；以里程碑分支或小批次 PR 合并，不将未验证的大型数据库迁移直接合入发布候选。
- Flyway migration 与代码同 PR；部署顺序遵循“先兼容 schema、再部署兼容服务、回填/切读、观察、最后移除旧路径”。
- 每次里程碑发布保存迁移日志、版本差异、权限验收、UI 验收和回滚说明。
- 不承诺对用户数据表执行逆向 DDL 回滚。数据迁移失败通过恢复备份、兼容读路径或前向修复处理。

## 7. 风险与应对

| 风险 | 影响 | 应对/计划缓冲 |
|---|---|---|
| 生产 schema 与代码迁移历史不一致 | V27 失败或破坏兼容 | Sprint 0 做只读 DDL 差异；先备份恢复副本演练 |
| 不同 JDBC 驱动返回元数据差异 | 资产树和 diff 不稳定 | 小范围连接器适配；对每驱动保存契约样例；保留原始 type 信息但不保存数据样本 |
| 目录暴露越权对象名称/字段 | 数据泄露 | 目录查询与资源授权取交集；撤权即时生效；负权限验收进入发布门 |
| 质量/入仓任务影响 BI 查询或业务源 | 在线体验下降、源端负载增加 | 分离在线/批处理连接池；设并发、超时、抽取速率和目标配额；以压测/监控调整 |
| 数仓选型与运维能力不匹配 | 成本、恢复或查询性能无法达标 | Sprint 0 评估数据量/时效/成本/团队运维能力，保留外部数仓作为受控目标选项 |
| 源目标语义或结构变化导致数据不一致 | 下游 BI 指标漂移 | 明确更新/删除/迟到数据口径；入仓差异门禁；先 staging 后发布并保留回退版本 |
| 自动字段迁移误伤图表 | 报表损坏 | 先 diff 和影响预览，改名依赖人工映射/批准，迁移有回滚点 |
| 范围扩张导致延期 | 关键闭环无法上线 | P0/P1/P2 切分；P2 设触发条件；每阶段冻结范围 |
| 外部通知和 API 环境不齐 | 无法生产验证 | 使用独立测试端点；无真实环境时状态标“待环境验收” |

## 8. 计划维护方式

每个 Sprint 结束按实际吞吐更新任务状态、剩余估算和风险；只调整未开始任务，不回写历史验收结论。范围、依赖或关键口径变化时记录 ADR，并同步更新任务清单、架构/验收文档和里程碑日期。

## 9. 后续扩展：独立同步执行引擎

- **DP-042（P2）**：评估 Apache SeaTunnel，作为独立于 BI 应用的同步执行引擎候选。
- 先完成 PostgreSQL、ClickHouse、SQL Server、Oracle 等实际源/目标组合的连接器和版本矩阵，再确定部署模式、插件管理、任务提交/状态回调、凭据引用、审计及故障恢复方案。
- 试点范围从多表定时批量同步开始；只有业务时效和源库日志权限满足时，再评估 CDC。
- 启动条件：当前应用内同步器在多表、跨连接器或吞吐方面形成明确瓶颈，或任务清单中的入仓增强进入排期。
