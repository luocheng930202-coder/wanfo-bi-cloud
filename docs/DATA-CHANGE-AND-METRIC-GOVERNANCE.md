# 结构变更与指标口径治理（DP-026 / DP-027）

## 结构变更迁移

1. 管理员在数据资产目录打开数据库表资产的“结构变化与影响”，查看事件的字段差异、下游数据集、质量规则、任务和流程。
2. 在影响预览中为每个受影响的数据集字段指定变更后的源字段，或显式选择删除；随后生成迁移计划。目标字段必须存在并保持相同类型。
3. 只有无阻断项的草案可审批。审批后才允许执行。结构化模型、手写 SQL 数据集、类型不兼容、删除字段依赖以及不完整映射均会阻断执行。
4. 字段重命名保留 BI 逻辑字段名，通过 `bi_dataset_field.source_name` 记录新的物理源字段，并重建 `union_sql` 投影。图表、看板和策略继续读取原逻辑字段标识。
5. 执行使用数据库事务并记录操作审计和修订快照。执行失败事务会回滚；状态另行记为 FAILED。已执行计划只有在字段仍与计划执行后的状态一致时才可回滚，回滚恢复字段映射和执行前查询定义。

接口：`GET/POST /bi/catalog/schema-changes/{eventId}/migration-plans`；`GET /bi/catalog/schema-migration-plans/{id}`、`GET /bi/catalog/schema-migration-plans/{id}/revisions`；以及该计划下的 `POST approve`、`POST execute`、`POST rollback`。以上变更管理 API 需要 `bi:resource:admin`。

目前按单表物理数据集执行；删除保护以数据集依赖为保守边界，因此数据集上任何图表、策略、质量任务、表单或流程引用都可能阻止字段删除。执行前需应用 V40 数据库迁移。上线前需要用临时源表验证添加、重命名、受依赖删除阻断、无依赖删除、失败回滚和人工回滚。

## 指标口径治理

指标定义在现有 `bi_metric.definition_json` 中保存业务定义、业务维度、统计粒度、单位、IANA 时区和负责人；已发布定义的 JSON 冻结在发布快照及 `bi_metric_history` 中。发布前必须补全业务定义、统计粒度、单位、时区和负责人，时区示例为 `Asia/Shanghai`。草稿保存与预览不强制完成全部治理字段。

指标页会提示同一数据集、相同度量字段和聚合函数，但业务定义/维度/粒度/单位/时区不同的指标组合。提示用于发现口径差异，不自动合并或阻止发布；由指标负责人决定是否为有效的不同口径。已发布消费者仍由 `bi_metric_usage` 记录，历史版本可查看当时冻结的定义和责任信息。

API：`GET /bi/metric/conflicts` 查询当前用户有权查看指标之间的口径差异；现有 `/bi/metric/{id}/history` 返回每次发布冻结的口径快照，`/usages` 查看消费者。该能力不自动判断业务定义是否正确，发布后的业务含义仍需指标负责人确认。

## 构建与验收

- 后端编译：`mvn -pl ruoyi-modules/ruoyi-bi -am -DskipTests compile`
- 前端生产构建：`npm run build:prod`
- BI 类型检查：`npm run typecheck:bi`
- 本地运行验收待办：应用 V40；以真实目录扫描生成一次字段变更；检查计划审核/执行/回滚、下游图表逻辑字段稳定；完善一项指标口径并发布；查看发布历史、消费者及冲突提示。
