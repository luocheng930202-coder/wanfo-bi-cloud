# 数据平台生产发布与恢复演练手册

> 对应 DP-031。本文是可执行检查表，不代表生产环境已经配置或完成演练。每次发布应复制“发布记录模板”，由发布负责人和数据库/平台运维共同签字。

## 1. 发布前门禁

### 变更审查

- 确认目标环境、分支、构建产物版本、数据库最高 Flyway 版本及待执行迁移；只允许向前迁移，检查迁移可重复部署且没有修改已发布迁移。
- 将前后端产物、容器镜像或部署包固定到不可变版本/摘要。核对配置变更、依赖版本、数据库连接用户权限和回滚兼容范围。
- 在测试/预生产执行相同产物部署、迁移、冒烟查询和权限正反例；关键查询/数仓物化没有对账通过时阻止发布。
- 检查备份最近成功时间、存储位置、可读性、剩余空间和恢复负责人；没有可用备份不得执行有破坏性的迁移或数仓全量替换。

### 安全配置

- 所有外部 UI/API 入口通过 TLS；内部服务链路按网络分区和数据敏感等级决定 TLS，并记录例外。
- 密码、API Key、数据库凭据、SMTP/企业微信令牌从密钥管理服务或部署密钥注入，不写入 Git、镜像层、命令历史、日志或文档。
- 生产账号最小授权：BI 元数据库迁移身份与运行身份分开；数仓目标写入身份只拥有目标 schema/table 必要权限；业务源连接只读且限制网络来源。
- 管理接口、Actuator、Grafana/Tempo/Prometheus 等运营端点限制网络和身份访问；审计导出及备份设置访问审计。

## 2. 发布步骤和回滚边界

1. 通知变更窗口，冻结结构变更和人工数据修复；记录当前版本、健康状态、数据源可用性、最新数仓水位和未完成任务数。
2. 对 **BI 平台元数据库** 和 **ClickHouse 分析目标** 分别创建一致性备份，记录备份 ID、时间、范围、校验结果和恢复位置。两类备份分别验证，不能把一个系统的备份视为另一个的备份。
3. 部署向后兼容的数据库迁移。运行迁移前后分别核对版本记录和关键表/索引；预计锁表或耗时超预算时中止并调整窗口。
4. 部署后端，再部署前端静态产物；执行健康检查、管理员和受限用户登录、目录/查询/任务中心/导出/订阅/数据 API 的只读冒烟及授权拒绝检查。
5. 核对数仓新鲜度、同步运行、行数/关键金额对账和查询错误率；观察至少一个完整业务周期或双方约定的观察时长后结束变更窗口。

**应用回滚：** 若数据库变更向后兼容，回滚到上一版应用产物并保留迁移后的 schema；停止新写入功能，核对积压任务，再制定修复版。不要自动执行“降级 SQL”。

**数据/schema 回滚：** 若迁移破坏数据或结构不兼容，先停止写入并隔离受影响服务；从发布前备份恢复到独立恢复环境，校验一致后按业务 RPO 决定切换或重放。恢复整库会丢弃备份时间点之后的事务，必须由数据所有者确认。ClickHouse 目标数据单独恢复，不要通过恢复 BI 元数据库代替。

**数仓发布回滚：** 优先使用平台已实现的 staging 校验和原子发布/交换语义；失败应保留旧表并保留 run 记录。禁止直接删除旧目标或手工更新 checkpoint 来掩盖不一致。确认失败原因和上次成功水位后，再通过受控全量重建或重跑修复。

## 3. 备份与恢复要求

### BI 平台元数据库（MySQL）

- 由 DBA 采用已批准的物理备份或一致性逻辑备份方案覆盖 BI 平台表、迁移版本表和必要的若依身份/权限数据。确认二进制日志/PITR 是否满足组织 RPO。
- 加密备份，写入异地或隔离存储；保留策略与法定审计期一致。记录工具版本、加密密钥引用、备份校验和及恢复权限。
- 恢复演练必须在隔离实例：先恢复底层库，再启动匹配版本应用；检查迁移版本、用户/菜单授权、目录资产、任务状态和审计查询。

### ClickHouse 分析目标

- 单独列出数据库、表引擎、分区、TTL、物化视图、字典和必要配置；确认所选备份工具/存储支持生产表引擎和 ClickHouse 部署拓扑。
- 对本地磁盘快照、ClickHouse 原生备份能力或经批准的 `clickhouse-backup` 方案选一种并验证。备份元数据和配置与数据分开保管；含敏感数据的备份加密并限制访问。
- 恢复演练覆盖 ODS、DWD、DWS/ADS 代表表，检查行数、分区范围、主键重复、代表性金额/数量汇总、物化视图依赖和 BI 数据集查询。
- 若从 ODS 重建下游模型，先确认源快照/同步 checkpoint 足以达到目标 RPO；记录需要重放的 run、分区和上游水位。

### 演练成功标准

每季度或按组织灾备政策执行；演练环境隔离生产写入。恢复时间目标（RTO）和恢复点目标（RPO）由业务与运维共同填写，不能用默认值替代。结果必须包含计时、数据校验、失败项、责任人和整改期限。

## 4. 容量和可观测基线

| 指标 | 记录口径 | 告警/门槛由谁确定 |
|---|---|---|
| BI API 可用性与延迟 | 按路由统计成功率、P50/P95/P99、超时与 5xx | 业务 SLA + SRE |
| 元数据库 | CPU、内存、连接数、慢查询、锁等待、磁盘、备份耗时 | DBA + SRE |
| ClickHouse | CPU、内存峰值、并发查询、查询耗时/失败、parts、磁盘增长、合并压力 | 数仓运维 + SRE |
| 入仓任务 | 各源/目标 run 耗时、行数、失败率、重试数、源/目标水位差、延迟 | 数据负责人 + SRE |
| 质量与发布 | 质量门禁失败、对账差异、新鲜度年龄、发布回滚数 | 数据治理负责人 |
| 审计与追踪 | 审计写入失败、归档积压、追踪采样率/存储量、敏感字段扫描 | 安全 + SRE |

采集至少一个代表性高峰周期作为基线。用生产规模附近的脱敏或合成数据压测查询并发、全量入仓、物化刷新和备份恢复；记录数据量、并发、硬件、软件版本、参数、热/冷缓存条件和瓶颈。未得到业务容量指标前不写死 TPS、延迟或磁盘容量承诺。
